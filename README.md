# MediaGrid

Автоматизированная медиасистема для хранения, каталогизации и предоставления доступа к медиафайлам.
Микросервисная архитектура, один репозиторий (монорепозиторий).

## Стек

| Компонент | Версия |
| --- | --- |
| Java | 21 |
| Maven | 3.10.0 |
| Spring Boot | 4.1.x |
| Spring Cloud | 2025.1.x |
| PostgreSQL (образ) | `postgres:18.6-alpine3.24` |
| Шина сообщений | RabbitMQ 4 |
| Веб-интерфейс | Node.js 26 (только сборка), React 19, TypeScript 6, Vite 8, Mantine 9 |
| Точка входа | nginx 1.30 |

## Структура

- `discovery/` — регистр служб (Eureka), порт 8761
- `config-server/` — центр конфигурации, порт 8888
- `auth-service/` — служба авторизации, порт 8100 (только через шлюз). Описание — в [auth-service/README.md](auth-service/README.md)
- `media-service/` — служба медиаданных, порт 8200 (только через шлюз). Описание — в [media-service/README.md](media-service/README.md)
- `storage-service/` — служба загрузки и хранения файлов, порт 8300 (только через шлюз). Описание — в [storage-service/README.md](storage-service/README.md)
- `processing-service/` — служба обработки (миниатюры, превью, перекодирование через ffmpeg; очередь задач), порт 8400 (только через шлюз). Описание — в [processing-service/README.md](processing-service/README.md)
- `web/` — веб-интерфейс и nginx, единственная точка входа для браузера (HTTPS на 443, с 80 — перенаправление): отдаёт интерфейс, `/api` передаёт шлюзу. Описание — в [web/README.md](web/README.md)
- `gateway/` — шлюз, порт 8080 внутри сети (наружу не публикуется). Запросы `/api/<раздел>/**` передаются службам: `auth` — авторизации, `media` — медиаданных, `files` — загрузки и хранения, `processing` — обработки. Маршруты — в `config/gateway.yml`. Шлюз проверяет токен доступа до передачи запроса: без токена доступны только вход, обновление, выход и выдача файла по подписанной ссылке; пути `/api/<раздел>/admin/**` — только администратору
- `config/` — настройки служб, которые раздаёт центр конфигурации: `application.yml` — общие для всех, `<имя службы>.yml` — для отдельной службы. Пароли здесь не хранятся, только подстановки вида `${POSTGRES_PASSWORD}`
- `common/` — общие контракты (события очереди, формат ошибок), без бизнес-логики
- `service-support/` — общий код прикладных служб (обработка ошибок, проверка токенов, настройка защиты, шина сообщений); подключается автоматически
- `infra/` — служебные файлы инфраструктуры (схемы базы данных и т. п.)
- `docker-compose.yaml` — запуск всей системы
- служебные модули и службы добавляются в корень репозитория по одному каталогу на службу

У каждой службы свой `pom.xml`; родительский `pom.xml` в корне хранит только версии и список модулей.

## Запуск окружения

```
cp .env.example .env     # замените пароли и секреты (STORAGE_LINK_SECRET, PROCESSING_CLIENT_SECRET)
docker compose up -d
```

Интерфейс — https://localhost, вход — `ADMIN_EMAIL` и `ADMIN_PASSWORD` из `.env`. При первом запуске создаётся самоподписанный сертификат (`certs/`), поэтому браузер один раз предупредит о нём. Если порты 80 и 443 заняты, задайте другие в `MEDIAGRID_HTTP_PORT` и `MEDIAGRID_HTTPS_PORT`.

### HTTPS

Обмен с браузером идёт по защищённому каналу (ТЗ, п. 4.1.5). Без него куки входа (`Secure`) работает только на `localhost`. Запросы на порт 80 перенаправляются на HTTPS. Исключения: проверка готовности `/healthz` и проверка Let's Encrypt `/.well-known/acme-challenge/`.

| Сертификат | Что сделать |
| --- | --- |
| Самоподписанный (по умолчанию) | ничего: создаётся при запуске на имя `MEDIAGRID_HOSTNAME` (по умолчанию `localhost`); браузер предупреждает |
| Свой | положить `fullchain.pem` (сертификат с цепочкой) и `privkey.pem` в `certs/` (или в `MEDIAGRID_CERTS_DIR`), перезапустить `web` |
| Let's Encrypt | см. ниже |
| Без HTTPS (разработка) | `MEDIAGRID_TLS=off` — только HTTP на 80 |

С настоящим сертификатом включается HSTS: браузер полгода не будет заходить на сервер без HTTPS. С самоподписанным HSTS не включается.

Let's Encrypt на сервере (certbot установлен на сервере, домен указывает на него):

```
# 1. Запуск с каталогом проверки (пока с самоподписанным сертификатом). В .env:
#    MEDIAGRID_HOSTNAME=media.example.com
#    MEDIAGRID_ACME_DIR=/var/www/acme
docker compose up -d
sudo certbot certonly --webroot -w /var/www/acme -d media.example.com

# 2. Подключить выпущенный сертификат. В .env:
#    MEDIAGRID_CERTS_DIR=/etc/letsencrypt
#    MEDIAGRID_TLS_CERT_FILE=live/media.example.com/fullchain.pem
#    MEDIAGRID_TLS_KEY_FILE=live/media.example.com/privkey.pem
docker compose up -d web

# 3. Продление (certbot делает его сам по расписанию) — с перечитыванием сертификата nginx:
sudo certbot renew --deploy-hook "docker compose -f /путь/к/mediagrid/docker-compose.yaml exec web nginx -s reload"
```

### Служебные порты

Наружу открыты только порты 80 и 443. База, шина, регистр служб и центр конфигурации доступны лишь внутри сети Docker. Чтобы заглянуть в них при отладке, подключите `docker-compose.debug.yaml`: он открывает служебные порты, но только для этой машины (`127.0.0.1`):

```
docker compose -f docker-compose.yaml -f docker-compose.debug.yaml up -d
```

| Что | Адрес при отладке |
| --- | --- |
| PostgreSQL | `localhost:5432` |
| RabbitMQ, панель управления | `localhost:5672`, http://localhost:15672 |
| Регистр служб (Eureka) | http://localhost:8761 |
| Центр конфигурации | http://localhost:8888/<служба>/default |
| Служебные точки шлюза | http://localhost:8081/actuator/gateway/routes |

## Требования к серверу

Сервер с Linux и Docker. Наружу нужны только порты 80 и 443. Для настоящего сертификата — доменное имя, указывающее на сервер.

| | Процессор | Память | Диск | Для чего |
| --- | --- | --- | --- | --- |
| Мини ([`docker-compose.small.yaml`](docker-compose.small.yaml)) | 2 vCPU | 3 ГБ | SSD 20 ГБ | проверка, несколько пользователей |
| **Минимум** | 2 vCPU | **4 ГБ** | SSD 40 ГБ + место под файлы | небольшая команда (до ~20 человек одновременно) |
| Рекомендуется | 4 vCPU | 8 ГБ | SSD 40 ГБ + место под файлы | десятки пользователей, видео 4K |

Профиль для небольшого сервера (2 vCPU, 3–4 ГБ): уменьшенная куча Java, сборщик Serial, облегчённая компиляция, меньший буфер PostgreSQL, RabbitMQ без активного ожидания.

```
docker compose -f docker-compose.yaml -f docker-compose.small.yaml up -d
```

**Почему столько памяти.** Система — семь служб на Java (Spring Cloud). Каждая занимает 165–285 МБ при любых настройках, вместе около 1,7 ГБ. Ещё нужны PostgreSQL и RabbitMQ (около 0,3 ГБ), операционная система (0,3–0,4 ГБ) и ffmpeg во время обработки видео (до 0,75 ГБ на Full HD). Размер загружаемых файлов на память не влияет: они передаются потоком.

**Диск.** Образы системы занимают 2,4 ГБ, операционная система с Docker — 4–6 ГБ. Видео, которое браузер не воспроизводит, хранится дважды: исходник и перекодированная копия примерно того же размера. Плюс миниатюра и превью у каждого файла. Обработке нужно свободное место на размер самого большого файла и его копии. Закладывайте объём медиатеки × 2.

**Процессор** почти целиком уходит на перекодирование: ffmpeg занимает все ядра, пока работает. Просмотр каталога нагружает мало.

Замеры (0.8.0). Сервер имитировался контейнером с жёстким потолком: 2 ядра, память без подкачки. Нагрузку создавал k6: пользователи по кругу открывают каталог, файл и миниатюру, с паузой около секунды.

| Сценарий (2 vCPU, 3 ГБ, профиль small) | Запросов/с | 95 % ответов | Ошибки | Процессор |
| --- | --- | --- | --- | --- |
| 10 пользователей | 31 | до 36 мс | 0 | ~0,6 ядра |
| 50 пользователей | 152 | до 76 мс | 0 | ~1,15 ядра |
| 10 пользователей во время перекодирования 2 мин Full HD | 34 | до 31 мс | 0 | обработка — до 1,9 ядра |

На этой имитации ролик Full HD на 2 минуты перекодировался за 49 секунд. Ядра машины, на которой мерили, быстрее типичных vCPU, поэтому на VPS перекодирование будет в 2–3 раза медленнее: час Full HD — примерно за 1–1,5 часа. На 2 ГБ система не запустилась: службы завершались из-за нехватки памяти.

## Среда разработки

- Java 21 и Maven 3.10 — для служб (`mvn verify`).
- Node.js 26 — только для разработки интерфейса (`web/`); в Docker интерфейс собирается сам. Ставится через fnm, который берёт версию из `web/.node-version`:

  ```
  scoop install fnm
  # в профиль PowerShell ($PROFILE):
  fnm env --use-on-cd --shell powershell | Out-String | Invoke-Expression
  fnm install 26
  ```

## Версии проекта

Формат `1.2.3` (ГЛОБАЛЬНАЯ.КРУПНАЯ.МЕЛКАЯ):

1. **Первое число** — глобальные релизы, законченное программное обеспечение.
2. **Второе число** — крупное обновление, не меняющее суть системы; возможно добавление службы (юнита).
3. **Третье число** — маленькие обновления, исправления ошибок и прочие правки.

До первого законченного релиза версия начинается с нуля: `0.2.0`, `0.3.0` и т. д.
Текущая версия: `0.8.0` (задаётся в родительском `pom.xml`, у модулей наследуется).
Смена версии во всех модулях одной командой:

```
mvn versions:set -DnewVersion=0.6.0 -DgenerateBackupPoms=false
```

Версия образа каждой службы совпадает с версией проекта.

Суффикс `-SNAPSHOT` означает версию в работе: например, `0.4.0-SNAPSHOT` — это будущая `0.4.0`, её сборки
перезаписывают друг друга. Версия без суффикса — выпуск, его содержимое больше не меняется (исправления
выходят следующей версией). Порядок выпуска:

1. работа ведётся под `X.Y.0-SNAPSHOT`, изменения записываются в `CHANGELOG.md` в раздел «в работе»;
2. при выпуске суффикс убирается (`mvn versions:set -DnewVersion=X.Y.0 ...`), раздел в `CHANGELOG.md` получает дату;
3. после коммита ставится метка `vX.Y.0`, и версия сразу переводится на следующую `-SNAPSHOT`.

Что вошло в каждую версию — в [CHANGELOG.md](CHANGELOG.md).
