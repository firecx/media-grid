Проект MediaGrid: самостоятельно разворачиваемая медиасистема (хранение, каталогизация и выдача изображений, видео, аудио через веб-интерфейс). Микросервисная архитектура, монорепозиторий: https://github.com/firecx/media-grid (ветка main). Прикладываю ТЗ.docx.

Решения
- Язык и каркас: Java 21, Spring Boot 4.1.x (в pom.xml 4.1.1), Spring Cloud 2025.1.x (2025.1.2). Ветка Spring Boot 3.5 снята с поддержки, поэтому выбрана 4.1.
- Сборка: Maven 3.10.0. Родительский pom.xml в корне хранит только версии и список модулей; у каждой службы свой pom.xml. Контекст сборки образов — корень репозитория, чтобы подтягивался модуль common.
- База данных: образ postgres:18.6-alpine3.24, том подключается к /var/lib/postgresql. Одна база, по одной схеме на службу: auth, media, storage, processing (infra/postgres/init.sql).
- Шина сообщений: RabbitMQ 4 (выбрана по умолчанию, не обсуждалась отдельно).
- Файлохранилище: пока локальная файловая система за интерфейсом StorageProvider; MinIO отложен. Служба медиаданных не знает, где лежит файл (в media.media_files нет полей хранилища); storage_backend и storage_key — в storage.stored_files, ключ связи — id записи каталога (mediaId). В 0.6.0 интерфейс StorageProvider пересмотрен под докачку и выдачу частями: name, size, append(key, поток, maxBytes) с TooMuchDataException, truncate, openRange, delete, directUrl (необязательная прямая ссылка хранилища, для MinIO).
- Версии проекта 1.2.3: первое число — глобальные релизы (законченное ПО), второе — крупное обновление, возможно с новой службой, третье — мелкие правки и исправления. Сейчас 0.8.0-SNAPSHOT (в работе веб-интерфейс; последний выпуск 0.7.0). Порядок выпуска: работа ведётся под X.Y.0-SNAPSHOT; при выпуске убрать суффикс, перенести раздел «в работе» в CHANGELOG.md под дату, после коммита поставить метку vX.Y.0 и перейти на следующую -SNAPSHOT. Версия образа службы равна версии проекта (переменная MEDIAGRID_VERSION). Смена: mvn versions:set -DnewVersion=0.6.0 -DgenerateBackupPoms=false. При каждой смене версии добавлять запись в CHANGELOG.md (новые сверху, разделы «Добавлено», «Изменено», «Исправлено», «Удалено»).
- Node.js (решено в 0.8.0, только для сборки и разработки интерфейса; в работающей системе Node нет — интерфейс отдаёт nginx): ветка 26 (LTS с 28.10.2026, поддержка до 30.04.2029). Закрепляется файлом .node-version (26), полем engines в package.json (>=26 <27) и образом сборки node:26-alpine. Менеджер пакетов npm (идёт с Node; corepack из Node 25+ убран), package-lock.json в репозитории, в Docker — npm ci. Интерфейс не входит в сборку Maven: mvn verify не требует Node. На машине разработчика Node ставится через fnm (scoop install fnm; FNM_DIR = %USERPROFILE%\scoop\apps\fnm\current, в профиле PowerShell: fnm env --use-on-cd --shell powershell | Out-String | Invoke-Expression); в Windows npm запускается как npm.cmd (важно для fnm exec).
- В русском тексте не использовать английские термины.
- Окончания строк: LF везде (.gitattributes: * text=auto eol=lf, главнее core.autocrlf), т. к. всё работает в контейнерах на Linux; *.cmd и *.bat — CRLF; медиафайлы и jar — binary. В Git Bash под Windows grep по умолчанию не видит CR: для проверки окончаний использовать file или git ls-files --eol, для замены — perl.

Состав служб (по ТЗ): discovery (регистр служб), config-server (центр конфигурации), gateway (шлюз), auth-service (авторизация), media-service (метаданные, поиск, теги), storage-service (загрузка и хранение, потоковая передача, ссылки с ограниченным сроком действия), processing-service (транскодирование, превью, очередь), позже веб-интерфейс. Поддержка устойчивости к сбоям, сквозная трассировка, централизованные журналы.

Сделано
- Корень: pom.xml, docker-compose.yaml (postgres, rabbitmq, discovery, config-server, gateway, auth-service, media-service, storage-service, processing-service; тома postgres-data, storage-data, processing-work), CHANGELOG.md, .env.example (MEDIAGRID_VERSION, ADMIN_EMAIL, ADMIN_PASSWORD, STORAGE_LINK_SECRET, PROCESSING_CLIENT_SECRET), .dockerignore, .gitignore, README.md.
- common: события FileUploadedEvent(mediaId, ownerId, contentType, sizeBytes), ProcessingCompletedEvent(mediaId, success, hasPreview, errorMessage), MediaDeletedEvent, единый формат ошибки ApiError. Ключей хранилища в событиях нет (с 0.7.0). Бизнес-логики нет.
- discovery (Eureka, порт 8761): стартер spring-cloud-starter-netflix-eureka-server. Образ собирается, контейнер здоров.
- config-server (порт 8888): режим native, читает каталог config/ (локально file:./config/, в контейнере том ./config:/config, переменная CONFIG_LOCATION). Регистрируется в discovery. Образ собирается, контейнер здоров, настройки раздаются (GET /<служба>/default).
- config/application.yml: общие настройки служб (адрес регистра через EUREKA_URL, prefer-ip-address, открытые точки health и info). Пароли в config/ не хранить, только подстановки ${...} из переменных среды службы.
- Устройство Dockerfile служб: COPY . . (лишнее отсекает .dockerignore, каталог config/ в образы не попадает), сборка mvn -pl <служба> -am с кэшем BuildKit для ~/.m2, запуск на eclipse-temurin:21-jre-alpine. Проверка готовности в docker-compose через wget на /actuator/health.
- Кэш балансировщика нагрузки отключён в discovery и config-server (они никого не вызывают). Службам, которые вызывают друг друга через балансировщик, подключать зависимость caffeine.
- gateway (порт 8080, служебные точки на 8081, наружу не публикуется): стартер spring-cloud-starter-gateway-server-webflux (старого spring-cloud-starter-gateway в 2025.1 нет; настройки под spring.cloud.gateway.server.webflux.*). Настройки берёт из config-server (CONFIG_URL), маршруты в config/gateway.yml: /api/auth/** → auth-service, /api/media/** → media-service, /api/files/** → storage-service, /api/processing/** → processing-service, путь передаётся без изменений (службы сами обслуживают /api/<раздел>/**). Точка /actuator/gateway/routes открыта только на чтение (management.endpoint.gateway.access: read-only). Проверено: регистрация в discovery, 503 для маршрутов к ещё не созданным службам, 404 для неизвестных путей, правка config/ подхватывается перезапуском без пересборки.
- Проверка токенов в шлюзе (gateway/src/main/java/io/mediagrid/gateway/security/SecurityConfig.java): без токена только POST /api/auth/login|refresh|logout и GET /api/auth/jwks; /api/*/admin/** — роль ADMIN (единое соглашение для всех служб); /api/** — роли USER или ADMIN (токен службы с ролью SERVICE не проходит); GET/HEAD /api/files/*/content — без токена (подпись ссылки); вне /api — закрыто (интерфейс отдаёт nginx в контейнере web, до шлюза доходят только /api); /actuator/** открыт, но служебные точки только на порту 8081. Открытые ключи: NimbusReactiveJwtDecoder по mediagrid.security.jwk-set-uri (http://auth-service/api/auth/jwks) через ReactorLoadBalancerExchangeFilterFunction. Заголовок Authorization передаётся службам как есть, службы проверяют токен сами (заголовкам вида X-User-Id не доверять).
- Ошибки шлюза в формате ApiError: ApiErrorWebExceptionHandler (404, 405, 502, 503, 504, 500) и обработчики 401/403 в SecurityConfig. Ответы служб передаются как есть. Отказ соединения со службой (ConnectException в цепочке причин, в том числе тайм-аут соединения Netty) — 503; тайм-аут соединения шлюза 2 с (httpclient.connect-timeout в config/gateway.yml): остановленная служба числится в регистре до 90 с. Тайм-аут ответа не задан — потоковая выдача файлов долгая.
- Общие параметры проверки токенов в config/application.yml: mediagrid.security.issuer (mediagrid-auth) и mediagrid.security.jwk-set-uri; auth-service берёт издателя оттуда же.
- Тесты шлюза: GatewaySecurityTest (подменяет декодер токенов тестовым ключом, служб нет — пропущенный запрос получает 503). Проверено и вживую в Docker. Замечание для ручных проверок из Git Bash: кириллицу в теле запроса curl передавать из файла (--data-binary @file), иначе уходит не в UTF-8.
- Пока не сделано в шлюзе: повторные попытки и размыкание цепи (ограничение времени размыкателя не должно обрывать долгую потоковую передачу файлов), ограничение частоты попыток входа.
- auth-service (порт 8100, наружу не публикуется; описание интерфейса в auth-service/README.md): Spring MVC, стартеры Boot 4.1 spring-boot-starter-webmvc, spring-boot-starter-security-oauth2-resource-server, spring-boot-starter-flyway + flyway-database-postgresql. Схема auth через Flyway (V1__init.sql), Hibernate ddl-auto: validate. Токен доступа RS256 на 15 минут (sub = id пользователя, roles, email, iss mediagrid-auth), ключ RSA создаётся при первом запуске и хранится в auth.signing_keys, открытые ключи на GET /api/auth/jwks. Обновляемый токен на 30 дней в куки mediagrid_refresh (HttpOnly, Secure, SameSite=Strict, Path=/api/auth), в базе только SHA-256; меняется при каждом обновлении, повторное предъявление заменённого отзывает цепочку (family_id). Роли ADMIN и USER, открытой регистрации нет, первый администратор из ADMIN_EMAIL/ADMIN_PASSWORD. Административные функции на /api/auth/admin/**. Ошибки в формате ApiError (traceId пока null). Настройки в config/auth-service.yml (раздел mediagrid.auth).
- Тесты прикладных служб: @SpringBootTest + MockMvc + Testcontainers (PostgreSQL в контейнере через @ServiceConnection). Тестовый application.yml не ходит в config-server, а импортирует file:../config/application.yml и file:../config/<служба>.yml, поэтому проверяются боевые настройки. Запуск: mvn -pl <служба> -am test. auth-service: 12 тестов, проходят; через шлюз в Docker проверены вход, /me, обновление по куки, административный список, 401 без токена, сохранность токена после перезапуска службы.
- Известные ограничения auth-service: выданный токен доступа нельзя отозвать до истечения (15 минут); нет ограничения частоты попыток входа; все службы ходят в базу одним пользователем PostgreSQL (отдельные пользователи на схему — позже).

- media-service (порт 8200, только через шлюз; интерфейс в media-service/README.md): каталог (media.media_files), категории (справочник, ведёт ADMIN по /api/media/admin/categories), теги (нижний регистр, создаются при использовании, INSERT ... ON CONFLICT), поиск через JPA Specification (q по названию и имени файла, type, status, categoryId, tag — несколько через «и», mine, ownerId, сортировка). Права: владелец — всё со своими; PUBLIC видят все вошедшие после загрузки; ADMIN — всё; недоступное — 404, чужое видимое на изменение — 403. Сущности превращаются в ответы внутри транзакции (open-in-view выключен, иначе LazyInitializationException на тегах); default_batch_fetch_size 100.
- Порядок загрузки файла (решено в 0.5.0): POST /api/media → запись PENDING_UPLOAD, её id = номер файла → загрузка в storage-service под этим id (storage проверяет права, вызывая GET /api/media/{id} с токеном пользователя, своих учётных данных у служб нет) → событие file.uploaded → UPLOADED → processing.completed → READY или FAILED (исходный файл доступен и при FAILED). PENDING_UPLOAD старше 24 ч удаляются по расписанию (ТЗ 4.1.9) с событием media.deleted.
- Шина (common/.../events/Events.java): тематическая точка обмена mediagrid.events, ключи file.uploaded, processing.completed, media.deleted; каждая служба-получатель объявляет свою постоянную очередь <служба>.<ключ> и <очередь>.dlq через точку mediagrid.events.dlx. Повторы: 3 попытки (spring.rabbitmq.listener.simple.retry в config/application.yml), затем .dlq. Преобразователь сообщений JacksonJsonMessageConverter с доверенным пакетом io.mediagrid.common.events. media.deleted публикуется после фиксации транзакции (@TransactionalEventListener AFTER_COMMIT); при сбое публикации остаётся лишний файл, но не запись без файла. RabbitMQ 4 не разрешает временные неэксклюзивные очереди — объявлять только постоянные или эксклюзивные.
- Проверка токенов в прикладных службах (MVC): NimbusJwtDecoder по mediagrid.security.jwk-set-uri через @LoadBalanced RestTemplate. Если ключи нельзя получить (служба авторизации недоступна), AuthenticationServiceException → 503 SERVICE_UNAVAILABLE (обработчик BearerTokenAuthenticationFilter через withObjectPostProcessor; в шлюзе — в ApiErrorWebExceptionHandler). Проверено вживую.
- Подключение к базе: spring.datasource.hikari.schema = схема службы (иначе запросы на чистом SQL идут в public).
- Важно для тестов: файлы из spring.config.import перекрывают тот файл, который их импортирует, поэтому значения из config/*.yml нельзя переопределить в тестовом application.yml (только задать отсутствующие подстановки).
- service-support (0.6.0): общий код прикладных служб MVC, подключается автоматически (AutoConfiguration.imports), в pom службы вместо common. Содержит ApiException и ApiExceptionHandler, CurrentUser, SecurityProperties, проверку токенов JwtDecoder (@ConditionalOnMissingBean — auth-service ставит свою, по локальным ключам), ResourceServerSecurity.apply(http, json) — общая настройка защиты без состояния с 503 при недоступности ключей (службе остаётся только authorizeHttpRequests), преобразователь сообщений шины (при наличии RabbitTemplate) и EventQueues.declare(служба, ключи…) — очереди с .dlq.
- Компоненты с @LoadBalanced (RestTemplate для ключей, RestClient.Builder в storage-service) объявлять с @Bean(defaultCandidate = false). Иначе они вытесняют стандартный RestClient.Builder, клиент регистра (Eureka) начинает искать сам регистр через балансировщик («No servers available for service: discovery») и служба не регистрируется. Получать такой компонент только с явным @LoadBalanced в месте внедрения.
- storage-service (порт 8300, только через шлюз; интерфейс в storage-service/README.md): PUT /api/files/{mediaId} — файл целиком или часть (Content-Range), HEAD → Upload-Offset/Upload-Length для докачки; тело пишется потоком на диск. Загружать может только владелец записи (права узнаёт через GET /api/media/{id} с токеном пользователя). Получив файл, публикует file.uploaded после фиксации; повторный PUT уже полученного файла при записи, ещё ждущей загрузки, публикует событие снова. Ссылки POST /{id}/links → /api/files/{id}/content?expires&download&signature (HMAC-SHA256 ключом STORAGE_LINK_SECRET, срок mediagrid.storage.link-ttl 4h); выдача без токена (шлюз пропускает GET/HEAD /api/files/*/content), с Range (206/416). Удаление по media.deleted. Ключ файла originals/<2 символа>/<id>, в Docker том storage-data:/data/storage. В config/storage-service.yml выключен formcontent-фильтр, чтобы тело PUT не читалось заранее.
- Spring HttpRange не считает ошибкой диапазон, начинающийся за концом файла (bytes=100-200 при размере 20 даёт 206): проверять start >= size вручную.
- Устойчивость в storage-service (MediaClient): RestClient с балансировщиком, тайм-ауты 2 с / 5 с; повторы org.springframework.core.retry.RetryTemplate (Spring 7, 2 повтора, 200 мс × 2, кроме ApiException); размыкатель Spring Cloud CircuitBreaker Resilience4j «media-service» (окно 10, минимум 5, 50 %, 15 с, ApiException не считается сбоем). Тесты: MediaClientTest на MockRestServiceServer.
- Ограничения storage-service: рассчитана на один экземпляр (локальный диск и блокировка одновременной загрузки в памяти); для нескольких — общее хранилище и блокировка в базе.
- Проверено вживую в Docker (0.6.0): файл 5 МБ двумя частями с докачкой, 409 при неверном сдвиге, статус UPLOADED, скачивание по ссылке без токена (совпадает sha256), Range 206 и 416, подделанная подпись — LINK_INVALID, удаление записи убирает файл с тома и из базы.
- Токены служб (0.7.0): auth-service выдаёт токен с ролью SERVICE (sub = имя службы) по POST /internal/auth/token с Authorization: Basic имя:секрет; службы и секреты — mediagrid.auth.service-clients (секрет ≥ 32 символов, хранится отпечаток SHA-256, сравнение за постоянное время). Константы ResourceServerSecurity.USER_ROLES и SERVICE_ROLE: пути /api/** всех служб — hasAnyRole(USER_ROLES) (CurrentUser.of ждёт UUID в sub), внутренние /internal/** — hasRole(SERVICE). Шлюз /internal/** наружу не пропускает (всё вне /api закрыто).
- Производные файлы в storage-service (0.7.0): таблица file_variants (media_id, kind THUMBNAIL|PREVIEW|PLAYBACK, content_type без параметров, size, storage_key; ON DELETE CASCADE). Внутренний интерфейс: GET /internal/files/{id} (исходник), PUT /internal/files/{id}/variants/{kind} (нужны Content-Type и Content-Length; каждая версия под новым ключом variants/<2>/<id>/<kind>-<uuid>, запись в базе переключается после полной записи, прежняя удаляется). Ссылки: тело {download?, variant?}, variant = original|playback|preview|thumbnail входит в подпись; playback без версии → ссылка на исходник (ответ сообщает фактический variant).
- processing-service (порт 8400, только через шлюз; интерфейс в processing-service/README.md; ffmpeg из apk в образе): file.uploaded → задача в processing.jobs (сообщение подтверждается сразу; очередь в базе, а не в шине — RabbitMQ закрывает канал при неподтверждённом сообщении дольше 30 мин, а перекодирование идёт часами). JobRunner берёт задачи lockNextQueued (FOR UPDATE SKIP LOCKED) по расписанию и сразу по событию, workers потоков. MediaProcessor: скачать исходник (StorageClient, токен ServiceTokens) → ffprobe → ProcessingPlan (перекодировать только то, что браузер не воспроизведёт) → снимки JPEG preview 1280 / thumbnail 320 → ffmpeg с -progress pipe:1 → сохранить производные. Виды сбоев JobFailure: Transient — повтор с паузой retry-delay×2^n (≤ 30 мин, max-attempts 5), Permanent — сразу FAILED, Gone — задача снимается. Размыкатель Resilience4j storageBreaker (ядро resilience4j, без ограничителя времени Spring Cloud — передачи долгие): пока цепь разомкнута, новые задачи не берутся. Отметки исполнителя раз в 30 с, задача без отметки дольше stale-after возвращается в очередь; при выключении — release; media.deleted снимает задачу и убивает ffmpeg (JobContext.cancel). Итог processing.completed отправляет JobNotifier (флаг notified, досылка каждые 30 с). Повторный file.uploaded для завершённой задачи — повторная отправка итога. API: GET /api/processing/{id} (владелец из ownerId события или ADMIN; этап, процент, метаданные), /api/processing/admin/jobs, POST …/retry.
- media-service: processing.completed для записи в PENDING_UPLOAD сначала переводит её в UPLOADED (события идут по разным очередям, итог может опередить file.uploaded).
- Проверено вживую в Docker (0.7.0, ffmpeg 8.1): AVI (MPEG-4+MP3) → MP4 H.264/AAC, MP4 H.264/AAC не перекодируется (playback → original), OGG Vorbis → M4A, JPEG 2000×1000 → превью 1280×640 и миниатюра 320×160, битый файл → FAILED с причиной, Range на playback 206, имя clip.mp4 при скачивании.
- Ловушки: в Jackson 3 отсутствующее поле примитивного типа в record — ошибка 400 (FAIL_ON_NULL_FOR_PRIMITIVES); необязательные поля тела объявлять Boolean/Long. Точку подключения тома (/data/processing) удалить нельзя («Resource busy») — очищать только содержимое. В тестах значения из config/*.yml переопределяются через @SpringBootTest(properties = …). - Нагрузочная проверка (0.8.0, k6 2.3 в контейнере в сети стека; сценарии в рабочей папке проверки, не в репозитории): просмотр каталога 200 пользователей — 600–640 запросов/с, p95 12 мс (с параллельным перекодированием 45 мс), ошибок нет; загрузка 1 ГБ одним запросом — 9 с, память служб растёт на 15–30 МиБ (поток); перекодирование 2 мин 1080p MPEG-4 → H.264 — 24 с на 12 ядрах (≈4,3 ядра в среднем, ffmpeg берёт все), память processing ~1,05 ГБ (Java ~300 + ffmpeg ~750). С пределами памяти (Java-службы 448–512 МБ, discovery/config 320, processing 1,5 ГБ с -Xmx256m, postgres/rabbitmq 384, web 64) всё работает; в покое стек занимает ~2,2 ГБ. RabbitMQ периодически показывает всплески процессора до 200 % (ожидание с активным опросом в Erlang) — на маленьком VPS отключать (+sbwt none +sbwtdcpu none +sbwtdio none), ещё не проверено. Для входа в нагрузочных сценариях передавать готовый токен: вход ограничен 10 попытками в минуту.
- Проверка на «VPS» (0.8.0): контейнер docker:dind с --cpuset-cpus 0,1 (видно и доступно 2 ядра) и --memory/--memory-swap (общий потолок, без подкачки), образы переносятся docker save | docker exec -i … docker load, нагрузка k6 снаружи на проброшенный порт. Профиль Java для малой памяти: -Xmx64–128m, -XX:+UseSerialGC, -XX:TieredStopAtLevel=1, -Xss256k, -XX:ReservedCodeCacheSize=40m, -XX:MaxMetaspaceSize=160m; postgres shared_buffers=64MB; rabbitmq +sbwt none. Итоги: 2 ядра + 2 ГБ — система не поднимается (каждая Java-служба на Spring Cloud 165–285 МБ даже с кучей 64–128 МБ, вместе ~1,7 ГБ; принудительные завершения по памяти). 2 ядра + 3 ГБ — работает: в покое ~1,95 ГБ памяти служб; 10 пользователей — 31 запрос/с, p95 36 мс, ~0,6 ядра; 50 пользователей — 152 запроса/с, p95 76 мс, ~1,15 ядра; перекодирование 2 мин 1080p — 49 с при 10 пользователях (p95 31 мс), processing пик 787 МиБ, память «VPS» у потолка (с кэшем файлов). Ядра машины разработчика быстрее типичных vCPU VPS — на сервере перекодирование в 2–3 раза медленнее. Образы на диске 2,4 ГБ. Пределы памяти на каждый контейнер ниже реального потребления Java (256 МБ) дают завершения по кругу — пределы ставить с запасом или только общий потолок. Решено: профиль docker-compose.small.yaml (настройки Java/PostgreSQL/RabbitMQ из этой проверки, без пределов на контейнеры) и раздел «Требования к серверу» в README; минимум для работы — 2 vCPU, 4 ГБ, SSD 40 ГБ + файлы × 2.
