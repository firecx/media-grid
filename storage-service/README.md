# Служба хранения (storage-service)

Приём файлов (с докачкой после обрыва), хранение и выдача по ссылкам с ограниченным сроком действия, с поддержкой частичной загрузки для перемотки видео и аудио. Порт 8300, наружу не публикуется: все запросы идут через шлюз по пути `/api/files/**`. Сведения о файлах хранятся в схеме `storage`, сами файлы — в каталоге `mediagrid.storage.root` (в Docker — том `storage-data`, `/data/storage`).

Служба не ведёт каталог и не решает, кому что видно. Номер файла — `id` записи службы медиаданных (`mediaId`). Права проверяет служба медиаданных: служба хранения запрашивает `GET /api/media/{id}` с токеном пользователя. Своих учётных данных у служб нет.

## Как загрузить файл

1. `POST /api/media` — создать запись в каталоге (статус `PENDING_UPLOAD`), запомнить её `id`.
2. `PUT /api/files/{id}` — передать файл. Загружать может только владелец записи.
3. Получив файл целиком, служба публикует `file.uploaded`, и запись переходит в `UPLOADED`.

Файл можно передать одним запросом или частями. Часть указывается заголовком `Content-Range: bytes <начало>-<конец>/<полный размер>`. Части передаются по порядку, без пропусков. Если связь оборвалась, полученное сохраняется:

```
HEAD /api/files/{id}            → Upload-Offset: 3145728, Upload-Length: 5242880
PUT  /api/files/{id}
     Content-Range: bytes 3145728-5242879/5242880
     <оставшиеся байты>
```

`PUT` без `Content-Range` начинает загрузку заново. Ответ на `PUT` — `{"mediaId", "receivedBytes", "expectedBytes", "complete"}` и те же заголовки `Upload-Offset` и `Upload-Length`.

Полный размер должен совпадать с `sizeBytes` записи, тело запроса — с заявленной частью. Тело читается потоком прямо из соединения и в памяти не накапливается.

## Ссылки на файл

`POST /api/files/{id}/links` с телом `{"download": false}` (по умолчанию) или `{"download": true}` выдаёт ссылку:

```json
{"url": "/api/files/{id}/content?expires=1767225600&download=false&signature=…", "expiresAt": "2026-01-01T00:00:00Z"}
```

Ссылку получит любой, кому видна запись (владелец, все вошедшие при `PUBLIC`, администратор). Срок действия — `mediagrid.storage.link-ttl`, по умолчанию 4 часа. Подпись — HMAC-SHA256 ключом `STORAGE_LINK_SECRET` (не короче 32 символов). Смена ключа делает недействительными все выданные ссылки.

`GET` и `HEAD /api/files/{id}/content` по ссылке не требуют токена: тег `video` не умеет передавать заголовок `Authorization`. Ответ:

- `Content-Disposition: inline` для воспроизведения или `attachment` для скачивания, имя исходного файла в UTF-8;
- `Accept-Ranges: bytes`. На `Range: bytes=…` служба отвечает 206 с `Content-Range`, а на часть за пределами файла — 416 с `Content-Range: bytes */<размер>`. Если частей несколько, выдаётся первая;
- `X-Content-Type-Options: nosniff` и `Cache-Control: private` не дольше срока ссылки.

## Удаление

Файл удаляется по событию `media.deleted` (очередь `storage-service.media.deleted`): так происходит при удалении записи и при очистке незагруженных записей старше 24 часов. Повторное событие ничего не ломает.

## Программный интерфейс

| Запрос | Токен | Описание |
| --- | --- | --- |
| `PUT /api/files/{id}` | да | загрузка файла или его части |
| `HEAD /api/files/{id}` | да | сколько уже получено (`Upload-Offset`, `Upload-Length`) |
| `POST /api/files/{id}/links` | да | ссылка с ограниченным сроком |
| `GET`, `HEAD /api/files/{id}/content` | нет, подпись | содержимое файла |

Ошибки — в едином формате `{"code", "message", "traceId", "timestamp"}`:

| Код | Состояние | Когда |
| --- | --- | --- |
| `INVALID_CONTENT_RANGE` | 400 | заголовок `Content-Range` не разобран |
| `SIZE_MISMATCH` | 400 | полный размер не равен `sizeBytes` записи или длина тела не равна заявленной части |
| `BODY_TOO_LARGE` | 400 | в теле больше данных, чем заявлено; часть отбрасывается целиком |
| `UNAUTHORIZED` | 401 | нет токена или он недействителен |
| `FORBIDDEN` | 403 | загружать или смотреть ход загрузки может только владелец |
| `LINK_INVALID` | 403 | подпись ссылки неверна |
| `LINK_EXPIRED` | 403 | срок действия ссылки истёк |
| `NOT_FOUND` | 404 | записи нет или она пользователю не видна |
| `UPLOAD_IN_PROGRESS` | 409 | этот файл уже загружается другим запросом |
| `UPLOAD_OFFSET_MISMATCH` | 409 | часть начинается не с `Upload-Offset` |
| `ALREADY_UPLOADED` | 409 | файл для записи уже загружен |
| `NOT_UPLOADED` | 409 | ссылку нельзя выдать: файл ещё не загружен |
| `SERVICE_UNAVAILABLE` | 503 | служба медиаданных или авторизации недоступна |

## Устойчивость к сбоям

Обращения к службе медиаданных (`MediaClient`) идут через балансировщик. Тайм-ауты: соединение 2 с, ответ 5 с. При сбое связи или ответе 5xx делается до 2 повторов с паузой 200 и 400 мс. Ответы «нет записи» и «нет прав» не повторяются.

Если из последних 10 обращений (не меньше 5) половина закончилась сбоем, цепь размыкается (Resilience4j, имя `media-service`). Тогда 15 секунд запросы сразу получают 503, не дожидаясь тайм-аутов, после чего служба пробует снова.

Если событие `file.uploaded` потерялось, повторный `PUT` уже загруженного файла публикует его снова.

## Настройки

`config/storage-service.yml`, раздел `mediagrid.storage`:

| Свойство | Переменная среды | Значение |
| --- | --- | --- |
| `root` | `STORAGE_ROOT` | каталог файлов, по умолчанию `./data/storage` |
| `link-ttl` | — | срок действия ссылки, по умолчанию `4h` |
| `link-secret` | `STORAGE_LINK_SECRET` | ключ подписи ссылок, обязателен, не короче 32 символов |

Файлы лежат по ключу `originals/<первые 2 символа id>/<id>`. Доступ к хранилищу скрыт за интерфейсом `StorageProvider`; сейчас реализовано только локальное хранилище (`LocalFileStorage`).

## Ограничения

- Рассчитана на один экземпляр: файлы на локальном диске, а защита от одновременной загрузки одного файла хранится в памяти. Для нескольких экземпляров нужны общее хранилище (например, MinIO) и блокировка в базе.
- Заголовки `Upload-Offset` и `Upload-Length` взяты по смыслу из протокола tus, но сам протокол не реализован.
