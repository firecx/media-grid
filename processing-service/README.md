# Служба обработки (processing-service)

Делает миниатюры и превью, перекодирует видео и звук, которые браузер не воспроизведёт, и сообщает каталогу итог обработки. Порт 8400, наружу не публикуется: ход обработки запрашивается через шлюз по пути `/api/processing/**`. Задачи и метаданные обработки хранятся в схеме `processing`. Для работы с файлами используются ffmpeg и ffprobe, они входят в образ.

## Как обрабатывается файл

1. Служба хранения получает файл целиком и публикует `file.uploaded`. Служба обработки ставит задачу в очередь (таблица `processing.jobs`) и сразу подтверждает сообщение.
2. Исполнитель берёт задачу из очереди и получает исходный файл через внутренний интерфейс службы хранения (`GET /internal/files/{id}`) с токеном службы.
3. ffprobe определяет формат, кодеки, длительность и размер кадра.
4. Делаются превью (до 1280 точек по большей стороне) и миниатюра (до 320 точек) в JPEG:
   - у изображения — из него самого;
   - у видео — кадр с 10 % длительности, но не дальше 10-й секунды;
   - у звука — из обложки, если она вложена в файл.
5. Если браузер исходный файл не воспроизведёт, делается версия для воспроизведения (см. ниже).
6. Результаты сохраняются в службу хранения (`PUT /internal/files/{id}/variants/{kind}`), в каталог уходит `processing.completed`, и запись становится `READY`. Если обработать не удалось, запись становится `FAILED`, но исходный файл остаётся доступным.

Очередь хранится в базе, а не в шине, по двум причинам. Во-первых, перекодирование большого видео идёт часами, а RabbitMQ закрывает канал, если сообщение не подтверждено за 30 минут. Во-вторых, ход обработки и её результат должны переживать перезапуск службы. Задачи раздаются через `SELECT … FOR UPDATE SKIP LOCKED`, поэтому несколько экземпляров службы не возьмут одну задачу дважды.

## Что перекодируется

Исходный файл не меняется никогда. Отдельная версия для воспроизведения (`playback`) делается только при необходимости:

| Вид | Воспроизводится как есть | Иначе |
| --- | --- | --- |
| Видео | MP4 (`video/mp4`) с H.264 (yuv420p) и звуком AAC или MP3 | MP4: H.264 и AAC, оглавление в начале файла. Подходящие дорожки копируются без перекодирования (например, H.264 из MKV) |
| Звук | MP3, AAC (MP4/M4A или ADTS), FLAC, WAV (PCM) | M4A (AAC 192 кбит/с) |
| Изображение | всегда | — |

Если версии `playback` нет, служба хранения по запросу ссылки на воспроизведение выдаёт исходный файл.

## Сбои и повторы

| Что случилось | Что будет |
| --- | --- |
| Служба хранения или авторизации недоступна | Задача возвращается в очередь. Повтор через 30 с, затем пауза удваивается (не больше 30 минут); после 5 попыток — `FAILED` |
| Подряд несколько таких сбоев | Цепь размыкается на 30 с (Resilience4j): исполнители не берут новых задач и не тратят на них попытки |
| Файл не распознан, ffmpeg завершился с ошибкой, превышено время | Сразу `FAILED`; в `error` — последние строки вывода ffmpeg |
| Запись удалена (`media.deleted`) | Задача снимается, запущенный ffmpeg останавливается, итог не отправляется |
| Служба выключается | Начатые задачи возвращаются в очередь |
| Служба упала посреди работы | Задачу, исполнитель которой не отмечался дольше 5 минут, возвращает в очередь любой экземпляр |
| Не удалось отправить `processing.completed` | Итог досылается каждые 30 с, пока не уйдёт |

Если служба обработки не работает, загрузка и просмотр не страдают (ТЗ, п. 4.1.4): файлы ждут в очереди со статусом `UPLOADED` и обрабатываются, когда служба вернётся.

## Программный интерфейс

| Запрос | Кто | Описание |
| --- | --- | --- |
| `GET /api/processing/{id}` | владелец файла, администратор | ход и итог обработки |
| `GET /api/processing/admin/jobs?status=&page=&size=` | администратор | очередь; `status` = `QUEUED`, `RUNNING`, `DONE`, `FAILED` |
| `POST /api/processing/admin/jobs/{id}/retry` | администратор | обработать заново завершённую задачу (например, после обновления ffmpeg) |

Ответ `GET /api/processing/{id}`:

```json
{
  "mediaId": "…",
  "status": "RUNNING",
  "stage": "TRANSCODING",
  "progress": 47,
  "attempts": 1,
  "nextAttemptAt": null,
  "error": null,
  "durationMs": 754000,
  "width": 1920,
  "height": 1080,
  "videoCodec": "hevc",
  "audioCodec": "aac",
  "transcoded": true,
  "hasPreview": true,
  "createdAt": "…",
  "startedAt": "…",
  "finishedAt": null
}
```

- `stage` (этап): `DOWNLOADING`, `ANALYZING`, `PREVIEW`, `TRANSCODING`, `SAVING`.
- `progress` — готовность задачи целиком, 0–100. Во время перекодирования считается по длительности, уже обработанной ffmpeg.
- `nextAttemptAt` — когда будет повтор после временного сбоя.
- `durationMs`, `width`, `height`, кодеки — метаданные обработки; неизвестное равно `null`.

Ошибки — в едином формате `{"code", "message", "traceId", "timestamp"}`. Чужая задача выглядит как несуществующая (404). `JOB_ACTIVE` (409) означает, что повтор не нужен: задача уже в очереди или выполняется.

## Вход в другие службы

Служба получает токен с ролью `SERVICE`: `POST /internal/auth/token` к службе авторизации, имя `processing-service`, секрет `PROCESSING_CLIENT_SECRET` в заголовке `Authorization: Basic`. Токен хранится в памяти и обновляется за минуту до истечения. Он открывает только внутренние пути `/internal/**`: шлюз их наружу не выпускает, а пути пользователей `/api/**` для него закрыты.

## Настройки

`config/processing-service.yml`, раздел `mediagrid.processing`:

| Свойство | Значение по умолчанию | Что это |
| --- | --- | --- |
| `work-dir` | `PROCESSING_WORK_DIR`, в Docker — том `processing-work` | временные файлы задачи; очищается при запуске |
| `workers` | 1 | сколько файлов обрабатывается одновременно |
| `poll-interval` | 5s | как часто смотреть в очередь (новые задачи берутся и сразу по событию) |
| `max-attempts`, `retry-delay` | 5, 30s | повторы при временных сбоях |
| `stale-after` | 5m | когда задача без отметки исполнителя считается брошенной |
| `job-timeout` | 6h | наибольшее время перекодирования |
| `transfer-timeout` | 1h | наибольшее время передачи файла между службами |
| `thumbnail-size`, `preview-size` | 320, 1280 | большая сторона миниатюры и превью |
| `client-secret` | `PROCESSING_CLIENT_SECRET` | секрет службы для получения токена |

Временному каталогу нужно место на размер самого большого файла и его перекодированной версии.

## Ограничения

- Поворот фотографий по метке EXIF не учитывается: превью снятого «боком» снимка может оказаться повёрнутым.
- Разрешение видео при перекодировании не уменьшается: из 4K получится 4K в H.264.
- Нет нескольких качеств и адаптивной передачи (HLS).

## Тесты

`mvn -pl processing-service -am test`:

- `ProcessingPlanTest` — решения «перекодировать или нет» на образцах ответа ffprobe;
- `ProcessingFlowTest` — от `file.uploaded` до `processing.completed` на PostgreSQL и RabbitMQ в контейнерах: итог, ход обработки и права, ошибка файла и повтор администратором, временный сбой с повтором, остановка при удалении записи, повторное событие. ffmpeg и служба хранения подменены; сам ffmpeg проверяется в Docker.
